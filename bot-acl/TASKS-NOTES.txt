Bot consultation and task implementation verification

Scope: bot-acl plugin. Both the synchronous ask_bot consultation tool and the
asynchronous bot_task tool are supported.

ask_bot: target, message, optional mode=new_session (default) or resume with an
exact target-owned session_id. No bot_chat mode and no canonical Bot Chat lookup,
creation, or continuation. No caller timeout_seconds: the handler rejects that
key explicitly, including value 0, and always runs the public CLI with
--run-budget 0 --max-turns 250. The reply is returned synchronously. Nested
consultations are disabled. Audit, stream parsing, session-evidence and
process-group cleanup behavior from 0.5.0 are retained.

bot_task actions: spawn, list, status, wait, steer, stop.
spawn admits a task and returns without waiting for child readiness. A bounded
startup thread retains the caller's contextvars. Spawn modes:

- new_session (default): session.create.
- resume: an exact target-owned stored session ID, checked read-only in the target
  profile's state.db before launch, then session.resume. Titles, "latest" and IDs
  belonging to another profile are rejected before a child starts.

No bot_chat mode: bot_task never looks up, creates, or continues a canonical Bot
Chat. No caller timeout_seconds: the handler rejects that key explicitly,
including value 0. The child has no wall-clock timer and no deadline. Explicit
stop still kills and reaps the dedicated child process group. Effects already
performed cannot be rolled back. Existing same-group ACL, parent ownership and
active-task limits apply. status/wait/stop/steer require task_id; list takes no
extra fields.

The verified parent session_id comes only from the tool runtime keyword arguments.
spawn.session_id is accepted only with mode=resume and is the target-owned stored
session. It never becomes the task owner key.

Transport: with the same-group ACL applied, ask_bot uses the installed public
CLI; bot_task uses the installed official TUI's tui_gateway.entry stdio JSON-RPC
subprocess, session.create, session.resume, prompt.submit, session.steer and
session.activate. No HTTP API listener or shared gateway changes. No private
function imports or core patches. The module entrypoint is shipped by Hermes; a
stable documented third-party compatibility guarantee has NOT been established.
Runtime discovery is used and a missing entrypoint fails closed, without another
transport resend.

Important capability boundary:
The installed TUI backend owns pending_steer replay in
_run_post_turn_followups. The plugin never duplicates that replay. The public
stdio results do not expose pending_steer plus a definitive drained/final marker,
so the plugin CANNOT certify exactly-once replay or finality. message.complete can
precede another automatic turn. Status includes finality_verified=false; observed
completed can return to running. The child is not killed on the first complete
event, preventing premature loss of backend-owned replay. It remains bounded by
explicit stop. A stop racing with a follow-up that has already begun cannot
retroactively prevent that execution.

Ownership refusal during prompt.submit (SESSION_NOT_OWNED / code 4090 / busy)
becomes target_busy with no automatic retry, resend or mode switch. Invalid resume
IDs and other startup failures become failed_unknown.

No claim is made that accepted guidance was consumed at a live tool boundary.
The returned backend result is preserved. No automatic resend is attempted.
Protocol tests create seeded sessions in temporary empty profiles to verify exact
session.resume without invoking a model; process-shared ownership is exercised
directly through the installed registry. A model-driven end-to-end
steering/replay test was not performed.
